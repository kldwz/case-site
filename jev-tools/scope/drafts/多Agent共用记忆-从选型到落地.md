# 我让三个 AI 助手共用同一份记忆：从选型到本地跑通

我电脑里同时跑着三个 AI 助手：CodeBuddy、Claude Code、Hermes。

它们各记各的。

在 A 里说过的事，到 B 里要重讲一遍。在 B 里定下的技术决策，到 C 里它一无所知。三个助手，三份互不相识的记忆。

这不是"AI 记性不好"的问题，是**记忆没有公共底座**。

花了几天把它打通，现在三个助手读写同一份记忆。这篇文章记一下完整过程：我想要什么、怎么选的、怎么装的、踩了什么坑、怎么验证它真的记住了。

---

## 一、先想清楚：我要的到底是什么

动手之前我先列了四条硬标准。这四条直接决定了后面所有的选择。

**1. 必须独立于 Agent 框架**

记忆要抽出来做单独一层，不能是某个框架的附属功能。否则我今天用一个助手，明天换一个，记忆就跟着作废。

**2. 数据必须在本地**

我的记忆里有大量没公开的项目的细节、收入目标、踩过的坑。这些东西放别人服务器上，我不踏实。

**3. 接入成本要低到"改一行配置"**

我不想为了记忆去改 Agent 的代码、写插件、维护分支。最好是配一个 MCP 服务就完事。

**4. 要能做事实抽取，不是简单的向量堆砌**

这一条最容易被忽略，也最关键。

如果只是把对话原文切片、向量化、检索时塞回上下文，那不叫记忆，那叫 RAG 聊天记录。真正的记忆要能**从对话里抽出事实**，并且在事实变化时**更新旧的那条，而不是新增一条冲突的**。

---

## 二、选型：为什么最后是 mem0

> 说明：这一节是我的取舍逻辑。备选方案我只在文档和 GitHub 层面看过，没实际部署，所以下面不涉及"某方案实测如何"的体验对比。

按上面四条去筛，市面上的方案基本分成两派：

**第一派：Agent 框架自带的记忆**

典型是 Letta（原 MemGPT）。它把记忆做进了 Agent 运行时里——核心记忆、归档记忆、召回记忆，分层管理，还有可视化界面。设计得很完整。

但它解决的是"**怎么让我的 Agent 记住事**"，不是"**怎么让多个不同的 Agent 共享记忆**"。

要用它的记忆，就得用它的 Agent。这直接违反我的第 1 条和第 3 条。

**第二派：独立的记忆层**

mem0 属于这一派。它只做一件事：给你一段对话，它负责抽取事实、去重、更新、检索。不绑定任何 Agent，对外就是一个 API。

再叠加一条：它有官方的 MCP 服务端（OpenMemory）。MCP 是什么？你可以理解成 AI 助手的 USB 接口——只要助手支持 MCP，接上就能用，不用改代码。

这正好命中第 3 条。

所以结论是 **mem0 + MCP**。

---

## 三、一个容易被忽略的选择：官方版还是第三方版

这里有个坑，值得单独说。

mem0 官方的 OpenMemory 在 `mem0ai/mem0` 仓库的 `openmemory/` 子目录下。它是一套完整服务：Docker Compose 起一整套，带 Web UI，通过 SSE 通信。

功能全，但对我的需求来说太重了——我不需要界面，我就想要一个安静的后台进程。

我最后用的是第三方 fork：`wonseoko/mem0-open-mcp`。它只做一个纯 stdio 的 MCP server，`pip install` 完给个配置文件就能跑。

**为什么要讲这个**：同一个开源项目，往往有"官方全功能版"和"社区精简版"。选哪个不是看谁更正统，是看你到底要不要那些功能。我明确不要 UI，所以我选轻的。

## 四、架构长什么样

```
CodeBuddy ─┐
Claude Code ─┼──(MCP)──→ 本地 mem0 MCP Server ──→ Qdrant 向量库
Hermes    ─┘                                    (本地 Docker)
                                                      │
                                                      └─→ 导出 Markdown 镜像 → Obsidian（人看）
```

四个组件：

| 组件 | 作用 |
|---|---|
| Qdrant | 向量存储，Docker 跑在本地 6333 端口 |
| mem0 MCP Server | 事实抽取 + 检索 + 更新去重 |
| 硅基流动 | 提供 LLM 和 Embedding（OpenAI 兼容接口） |
| Obsidian | 定期把记忆导出成 Markdown，人可以直接翻 |

**最关键的一个设计：`user_id` 统一。**

三个 Agent 写记忆时都必须带上 `user_id = "wangwang"`。这个 ID 就是记忆归一的钥匙——ID 不同，就是三份记忆；ID 相同，才是一份。

## 五、三个 Agent 怎么接

全部指向同一个二进制、同一份配置文件：

```json
{
  "mcpServers": {
    "mem0": {
      "type": "stdio",
      "command": "~/mem0_mcp_env/bin/mem0-open-mcp",
      "args": ["stdio", "-c", "~/mem0_scripts/openmemory-mcp.yaml"]
    }
  }
}
```

CodeBuddy 写进 `~/.codebuddy/.mcp.json`，Claude Code 写进 `~/.claude.json`，Hermes 写进 `~/.hermes/config.yaml`。

三处配置一模一样。这也是 MCP 的好处——接入这件事，真的就是复制粘贴。

服务端配置 `openmemory-mcp.yaml` 里有几个关键点：

```yaml
server:
  user_id: "wangwang"        # 三个 Agent 共用，记忆才归一

llm:
  config:
    model: "deepseek-ai/DeepSeek-V3.2"   # 负责抽取事实

embedder:
  config:
    model: "Qwen/Qwen3-Embedding-4B"
    embedding_dims: 2560                  # 必须和下面一致

vector_store:
  provider: "qdrant"
  config:
    collection_name: "wangwang_memory"
    host: "127.0.0.1"                     # 注意不是 localhost
    port: 6333
    embedding_model_dims: 2560            # 必须和上面一致
```

## 六、踩的坑（这部分最值钱）

### 坑 1：Python 版本

mem0 2.x 用了 `X | None` 这种新语法，**Python 必须 ≥ 3.10**。我一开始用系统自带的 3.9，直接报错。

### 坑 2：`localhost` 不通，得写 `127.0.0.1`

这个是真卡了我一会儿。

我的机器上 `localhost` 优先解析成 IPv6 的 `::1`，而 Qdrant 容器只监听 IPv4。结果就是连不上，报 503 或者超时。

**写 `127.0.0.1`，别写 `localhost`。**

### 坑 3：Embedding 模型维度的坑

我用的模型服务商，DeepSeek 系列**没有 embedding 模型**。得换成 `Qwen/Qwen3-Embedding-4B`。

然后它的维度是 **2560**，不是常见的 1536 或 768。

这个数字要在两个地方写，而且必须一致：`embedder.config.embedding_dims` 和 `vector_store.config.embedding_model_dims`。少写一个，或者两个不一致，Qdrant 建 collection 就会维度冲突。

### 坑 4：API 的调用方式不统一

这个坑很隐蔽，mem0 的 Python SDK 里：

```python
m.add(messages, user_id="wangwang")              # user_id 是顶层参数
m.get_all(filters={"user_id": "wangwang"})       # 却要包在 filters 里
m.search(query, filters={"user_id": "wangwang"}) # 同样要 filters
```

写和读的参数姿势不一样。不查文档很容易以为 `add` 也要传 filters。

### 坑 5：它会静默丢弃内容

这个是上线之后才发现的，**最阴的一个**。

`add_memories` 不是原样存储。它会先让 LLM 做"事实抽取"，只有抽取出**关于用户的事实陈述**才会入库。

我试过塞一段纯操作指令进去——比如"以后遇到 XX 情况就做 YY"这种规则清单——返回结果**是空的**。没有报错，没有警告，就是静静地什么都没存。

**结论**：记忆库只适合存"事实"（旺旺是谁、在做什么、偏好是什么）。规则、清单、流程这类东西，就该写进配置文件或笔记里，别指望塞进记忆库。

## 七、怎么验证它真的"记住了"

光能写入不叫记住。我写了个验证脚本，测三件事。

**测试 1：能不能写入**

塞四条事实进去，全量读出来看在不在。

**测试 2：会不会更新（这是核心）**

先写一条"目标是月入 1 万"，再告诉它"目标改成 3 万"。

**判据：库里应该只有一条，内容变成 3 万。**

如果变成两条——一条 1 万一条 3 万——那这个记忆系统就是废的。以后检索会同时召回两个矛盾的答案，比没有记忆还糟。

**测试 3：语义检索准不准**

用"靠什么赚钱"去查"在做 AI 教学、AI 工具、SEO"这条记录。

注意这两个句子的**关键词完全不重叠**。这测的是 embedding 的语义能力，不是字符串匹配。能召回，才说明是向量检索在干活。

## 八、还有一个没解决的担忧

回头说个一开始就在困扰我的问题。

我最早担心的是：**Agent 每次提问，会不会把整个记忆库灌进上下文？** 那太烧 token 了。

现在这套架构下，答案是不会——mem0 是检索式的，只把相关的那几条捞出来带上。

但这也带出一个新的使用原则：

**记忆库要存"指针"，不要存"内容"。**

比如我关注某个开源项目，记忆里应该记"旺旺关注 XX 项目，用于 YY 场景，链接在他的书签库 `wiki/bookmarks/` 下"，而不是把项目 README 全文塞进去。

需要细节的时候，Agent 顺着指针去读文档。**记忆是索引，不是硬盘。**

这一点我还在摸索，目前的习惯是定期把记忆导出成 Markdown 镜像到 Obsidian，自己翻一遍，手动清理掉那些不该存在的"内容型"记忆。

## 一句话总结

**记忆共享这件事，难的不是技术，是想清楚"记忆里该放什么"。**

技术部分其实就三步：起个向量库、跑个 MCP 服务、三个 Agent 配同一个 `user_id`。

真正花时间的是后半段——发现它会静默丢弃指令类内容、发现存坏了会召回矛盾答案、发现记忆应该当索引用而不是当硬盘用。

这些坑，不跑一遍是不知道的。
